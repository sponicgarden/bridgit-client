# Installable applet packages

One file installs a whole applet on a Bridgit phone. The owner approves it once, on one review screen. The phone then creates every part itself and keeps it running with no agent online.

- Format: the template registry's own `bridgit-template/1` definition, with `runtime.adapter: "bridgit.package.v1"`. Android also accepts the legacy `android.package.v1` name.
- Parts: up to 5 watches, one schedule, a single `processing.workflow` or up to four named `processing.flows`, up to 3 tables and one card. All are optional, but there must be at least one.
- Blanks: typed values the owner (or you) fill in: camera, interval, sensitivity, time and so on.
- Ready-made examples: every recipe has one at `https://bridgit.cc/recipes/<id>/applet.json`, for example [room-change-watcher](https://bridgit.cc/recipes/room-change-watcher/applet.json) or [situation-counter](https://bridgit.cc/recipes/situation-counter/applet.json) (needs API revision 71: its `situation` blank takes a library id from `GET /v1/situations` or the owner's own words).
- Needs API revision 69 or later (`GET /v1/health` → `api_revision`).

## Customization and template updates

**Control agents:** follow [Modifying applets and templates](https://bridgit.cc/learn/builder/modifying-applets.md) before changing an installed copy. Keep template ancestry, personal requirements and settings. On API revision 101+, use the development snapshot and guarded `change` workflow in that guide. Background template checks prepare merge tasks; the update endpoint still accepts your complete personal package and does not resolve conflicts for you. A successful validation is not proof that personal behavior or history will survive.

## What the owner does

1. Opens an Import link (the **Import to my phone** button on a recipe page, a QR code, or `bridgit://install?…`), or an `applet.json` file.
2. Reads one screen: what each part does and how often, what it can use, the worst-case paid model cost, and anything switched off on the phone. Changes any blank.
3. Taps **Approve and install** (with fingerprint or PIN if the phone asks for it).
4. Later, in **Applets › Installed applets**, they can Open its card, Pause/Resume, Check for update, or Remove it.

Nothing runs and nothing is granted before Approve. Each installed applet gets its own entry under Agents. That entry holds only the permissions the file declares, and no key can use it. Phone switches still apply: if Camera is switched off, the review says so and the install is refused.

### Requirements and owner setup

Declare every capability in `permissions.required` and any on-device engines in `runtime.engines`; workflow steps also contribute their required scopes. Do not add settings links or permission prompts to a template. Bridgit derives setup from these declarations and its device capability registry.

The review returns the existing `blockers` messages plus `requirements`, an array of `{message, action, target, label}` for missing prerequisites. The owner sees an action beside each requirement: enable a device feature, request Android permission, open the relevant system settings, or see alternatives when the device cannot support it. Actions are generated by Bridgit, never executed from template-supplied URLs. Clients should display unknown actions as explanatory text, not invent an intent.

Setup consent is separate from installation: enabling a feature affects Bridgit on this device and can also affect existing authorized agents. Paid workflow questions require explicit feature consent. Returning from setup refreshes the review; the final **Approve** action still checks every prerequisite before installing. Denied Android permissions offer app settings; unsupported requirements explain how to choose a compatible applet.

## What an agent does

| Call | Does |
| --- | --- |
| `POST /v1/applets/validate` | Dry run. Returns exactly what the owner would review, or the errors, plus `package`: the complete file with the registry's extra sections filled in. Stores nothing. |
| `POST /v1/applets/install` | Asks the owner (202, `awaiting_owner`). Then `applet.installed` (with `instance_id`) or `applet.declined` arrives in `/v1/events`. |
| `GET /v1/applets/installed` | The applets you asked for: status, config, the watch ids they run. |
| `POST /v1/applets/installed/{id}/update` | A complete personal revision. API 101 requires `change` with the snapshot revision, intent, acceptance and evidence; agent edits wait for owner review. Older versions may apply immediately without new permissions. |
| `POST /v1/applets/installed/{id}/pause` | `{"paused":true}` or `false`. |
| `DELETE /v1/applets/installed/{id}` | Removes every part and its permissions. `left_behind` is empty when nothing is left. |

The body is one of:

- `{"package": {…}}`: the file itself.
- `{"url": "https://bridgit.cc/…/applet.json"}`: bridgit.cc only.
- `{"template": "<registry key>", "revision": N}`: built-in templates, or published templates of the account the phone is linked to.

Add `"config": {…}` to fill blanks. Your agent needs the **Install applets** permission.

Updates change a running applet after the required review:

- Send the whole new file with a higher `version`. The phone recompiles it and swaps in only the parts that changed.
- A watch whose filled request is unchanged keeps its id and its counts.
- A changed watch is replaced, and the card is re-pointed at the new watch id.
- The owner's blank values carry over.
- If the new revision no longer accepts a carried-over value, the update is refused rather than silently reset.

## The file

```json
{
  "format": "bridgit-template/1", "id": "room-change-watcher", "version": "2.0.0", "kind": "applet",
  "name": "Room change watcher", "summary": "A free image-change trigger…",
  "runtime": {"adapter": "bridgit.package.v1", "applet_key": "room-change-watcher", "supports_dynamic_execution": false},
  "config_schema": {"type": "object", "additionalProperties": false, "required": ["camera", "interval_s"],
    "properties": {"camera": {"type": "string", "enum": ["rear", "front"]}, "interval_s": {"type": "integer", "minimum": 30, "maximum": 3600}}},
  "defaults": {"camera": "rear", "interval_s": 30},
  "processing": {
    "watches": [{"id": "main", "request": {"label": "Room image changes", "data": ["camera"], "camera": {"$input": "camera"},
      "model": "none", "interval_s": {"$input": "interval_s"}, "local": {"change_check": true, "sensitivity": "normal"}}}],
    "schedule": {"manifest": {"…": "a POST /v1/schedule manifest"}},
    "workflow": {"…": "a workflow.propose body"}
  },
  "permissions": {"required": ["camera", "interactions", "watches"], "optional": [], "remote": [], "automatic_grants": false},
  "ui": {"inputs": {"camera": {"label": "Camera", "help": "The camera that faces the room."}},
         "card": {"title": "Room change watcher",
                  "sources": {"status": {"watch": {"$watch": "main"}, "read": "status"}},
                  "pieces": [{"type": "metrics", "items": [{"label": "Checks", "value": {"$source": "status.checks"}}]},
                             {"type": "buttons", "items": [{"label": "Pause", "do": {"pause_applet": true}}]}]}}
}
```

Leave out `observation_schema`, `metrics`, `lifecycle`, `migration` and `data_policy`. The phone doesn't need them. The template registry does: `POST /v1/applets/validate` returns `package`, the complete file with those five filled in (and `permissions.required` too, if you left it out). Publish that file.

## Flows

A flow is a trigger, then 1 to 32 steps the phone runs on its own. Put one in `processing.workflow`, or up to 4 in `processing.flows` (each with an `id`, lowercase, 1-24 characters). The owner's review shows each flow as one plain sentence.

```json
"processing": {"flows": [{"id": "dinner", "name": "Dinner check",
  "trigger": {"type": "called"},
  "steps": [
    {"id": "shot", "type": "photo", "camera": {"$input": "camera"}, "keep": true},
    {"id": "look", "type": "ask_model", "model": "clef", "photo": {"$step": "shot.photo"},
     "questions": {"food": {"type": "choice", "instructions": "Is there food left in the bowl?",
       "criteria": {"full": "Most of the food is there", "some": "Some is left", "empty": "The bowl is empty"}}}},
    {"type": "record", "table": "meals", "row": {"bowl": {"$step": "look.answers.food"}, "photo": {"$step": "shot.photo"}}},
    {"id": "ask", "type": "ask_owner", "only_if": {"step": "look.answers.food", "is": "full"},
     "title": "No dinner yet", "text": "The bowl still looks full. Remind the family?", "choices": ["Remind them", "It's fine"], "wait_s": 600},
    {"type": "alert", "only_if": {"step": "ask.choice", "is": "Remind them"},
     "text": "Dinner check: the dog hasn't eaten yet.", "destinations": ["<owner-approved destination id>"], "on_error": "retry", "retries": 2}
  ]}]}
```

The watch's 18:00 rule starts it with `"do": {"flow": {"$flow": "dinner"}}`.

**Triggers:**

| Trigger | Starts when |
|---|---|
| `{"type": "called"}` | A watch rule or a schedule action names it in `do.flow` (or you call `workflow.run`). Values handed over with `with` are read as `{"$trigger": "with.<name>"}`; declare them in the trigger, e.g. `"with": {"note": "text"}`. |
| `{"type": "button"}` | The owner taps it, or a card button with `{"run_workflow": true}` runs it. |
| `{"type": "watch", "watch": {"$watch": "main"}, "on": "match"}` | That watch matches, or for a change-only watch, the picture changes. Use `"on": "rule", "rule": "<id>"` for a tally rule. |
| `{"type": "interval", "seconds": 900}` | Every 30 s to 24 h. |
| `{"type": "charging"}` | The phone is plugged in. |
| `{"type": "geofence", "latitude": …, "longitude": …, "radius_m": 200}` | The phone arrives within 100-10,000 m of a place. |

**Steps** (each may have `id`, `only_if` and `on_error`):

| Step | Fields | Result |
|---|---|---|
| `photo` | `camera` (`rear`, `front` or `lan:…`), `keep` (keep it for a table or gallery) | `photo`, `taken_at`, `camera` |
| `ask_model` | `model` (`jev`, `clef`, or `glm`), `questions` (as in watches), `photo` (`{"$step": "<photo step>.photo"}`) | `answers.<id>` (the choice, or the likelihood 0-1 for a `noul` question), `confidence.<id>`, `cost_usd` |
| `ask_owner` | `title`, `text`, `choices` (2-6), `wait_s` (30-3600, default 300) | `choice`, or `timed_out: true` |
| `notice` | `title`, `text`, `priority` (`normal` or `urgent`) | `interaction_id` |
| `speak` | `text` | |
| `ring` | `seconds` (1-30) | |
| `alert` | `text`, `destinations` (1-3 owner-approved recipients) | `alert_id` |
| `record` | `table`, `row` (column values) | `row_id` |
| `wait` | `seconds` (1-300) | |
| `stop` | none; use with `only_if` | ends the run |
| `event` | `text`: tells your agent (`workflow.signal`) | |

- **Results:** `{"$step": "<id>.<path>"}` and `{"$trigger": "<path>"}` stand for a whole value. Text fields also take a list of texts and references, joined: `"text": ["Bowl: ", {"$step": "look.answers.food"}]`. A reference must name an earlier step. A step that was skipped or failed gives nothing.
- **Conditions:** `"only_if": {"step": "look.answers.food", "is": "full"}` (or `"trigger": "<path>"`), with exactly one test: `is`, `is_not`, `in`, `at_least`, `below`, `exists`. Text compares without case.
- **Errors:** `"on_error": "stop"` (the default; the run ends as failed), `"skip"`, or `"retry"` with `"retries": 1-3`. A failed run doesn't switch the flow off.
- **Paid steps** (`ask_model`) count against the applet's `budget`, at most 4 per run. `ask_model` needs the owner's **Jev and Clef questions** switch in Agent permissions.
- **Every run is logged:** the card's `{"runs": "workflow"}` source and `workflow.runs` show each step: `ok`, `skipped`, `failed` (with the reason) or `not_run`.

## Doing things: the one `do`

Watch rules and schedule actions say what to do with one `do` (card buttons have their own, under Card pieces):

| `do` | Does |
|---|---|
| `{"flow": {"$flow": "<id>"}, "with": {…}}` | starts one of the applet's flows |
| `{"step": {"type": "notice", …}}` | runs one step (`notice`, `speak` or `record`) without writing a flow |
| `{"method": "GET", "path": "/v1/…"}` | one raw call, as before |

## Card pieces

The card is usually a list of pieces. The phone draws them in Bridgit's own style, with no HTML, CSS or script; custom HTML (below) is only for what pieces can't draw.

```json
"card": {
  "title": "Voice notebook",
  "sources": {"clip": {"reply": "clip"}, "notes": {"table": "notes", "limit": 20}},
  "pieces": [
    {"type": "buttons", "items": [{"label": "Record 10 seconds", "style": "primary", "into": "clip",
      "do": {"method": "POST", "path": "/v1/mic/record", "body": {"duration_seconds": 10, "transcribe": true, "return_audio": false}}}]},
    {"type": "draft", "id": "note", "label": "Note", "value": {"$source": "clip.transcript"}, "max": 1024},
    {"type": "buttons", "items": [{"label": "Save note", "confirm": "Save this note?", "do": {"record": "notes", "row": {"text": {"$draft": "note"}}}}]},
    {"type": "timeline", "items": {"$source": "notes.items"}, "time": "at", "label": "text"}
  ]
}
```

For a portable transcript button, declare `mic` and `interactions`, request 1–30 seconds, and set `transcribe: true` and `return_audio: false`. The reply supplies `transcript` and an ISO 8601 `recorded_at`. The owner can edit the draft before confirming the row. On Apple devices this requires microphone permission and an available on-device recognizer for the current language.

- **Pieces**: `header`, `status`, `text`, `note`, `metrics`, `gallery`, `video`, `table`, `timeline`, `people`, `devices`, `draft` and `buttons`. 1 to 24 of them.
- **Sources** say where a piece's data comes from: a watch's `tally` or `status`, the applet's flow `runs`, a `table`, kept `photos`, one read-only `call` (a `GET`), or a button's `reply` (its `into`). Up to 8.
- **`{"$source": "notes.items"}`** is a whole value, like `$input`. A missing path shows the piece's `empty` text.
- **Buttons** do one thing each: `refresh`, `pause_applet`, `run_workflow`, `record` (a row into a table), or one API call (`method`, `path`, `body`), run as the applet.
- **The phone sets the card's state** (loading, empty, stale after `fresh_s` seconds, paused, error). Change the words with `states`, for example `{"empty": "Nothing yet."}`.
- **Values have formats**: `number`, `minutes`, `time`, `ago`, `celsius`, `percent`, `money`, `words` and more.

Each recipe's `applet.json` illustrates its declared actions on a supported host, and `GET /v1/samples?id=pieces-status` is a complete pieces card you can post on its own (`POST /v1/interactions` with `kind: "pieces"`).

**Custom HTML is the escape hatch.** Instead of `pieces`, a card may name an HTML asset: `"card": {"asset": "card.html", "title": "…", "data": {"resource_id": {"$watch": "main"}}}` with `"assets": {"card.html": {"media_type": "text/html", "text": "<!doctype html>…", "sha256": "…"}}`. The asset is at most 48 KB (the whole package at most 128 KB), runs in the card sandbox, and reaches the phone through `Bridgit.act`. A card is pieces or HTML, not both. This is a different limit from an HTML card an agent posts directly with `POST /v1/interactions` (`kind: "html"`), which can be up to 256 KB.

## Tables

A table keeps rows on the phone, such as saved receipts or notes. The owner can see and delete them in **Installed applets › (applet) › Data**.

```json
"processing": {"tables": [{"id": "notes", "label": "Notes",
  "columns": {"text": {"type": "text", "label": "Note"}, "source_at": {"type": "time", "label": "Recorded at"}},
  "keep_days": 365, "max_rows": 1000, "share_with_installer": false}]}
```

- Up to 3 tables, each with 1 to 16 columns. Column types: `text`, `number`, `integer`, `boolean`, `time`, `date`, `choice` (with `options`), `photo`, and `json` (object or array, with a required `description` of its contents and structure). JSON values remain structured, never encoded strings; they share the 4 KB whole-row limit and may nest at most 8 levels.
- Rows are written by a `record` button on the card, or a `record` step in the workflow (`{"id": "save", "type": "record", "table": "meals", "row": {"activity": {"$step": "look.answers.activity"}}}`).
- Every row also gets `id`, `at` and `by`. Old rows go after `keep_days` (default 90), and the oldest go first past `max_rows` (default 1000).
- Owner control agents with `applet_install` can read and edit all applet tables with their existing key, regardless of who installed the applet or `share_with_installer`. No second approval is needed. The sharing flag only restricts non-control applet principals; it never removes owner-control access. Key, grant and capability checks still apply.

### Uniform data contract for every template

Applets may persist domain records **only** in `processing.tables`, with stable table/column ids, useful labels and typed values. Store photos as `photo` columns with kept refs; link derived records to their source photo using the same ref. Use a `choice` column for processing state (for example `new`, `reading`, `done`, `failed`) and mark completion only after saving results. For structured blobs declare a column such as `{"type":"json","description":"Workout result: score:number, moves:[{label,count}]."}`. Undeclared `/applet/records` writes are refused for applet principals; legacy records remain readable for migration into declared tables. Do not keep the only copy of domain records or processing status inside HTML, localStorage, rendered text or a custom portal. Stateless templates need no table.

Custom HTML cards use `GET /v1/applet/tables` to discover their own declarations, `GET /v1/applet/tables/{table}/rows` to read, `POST` with `{"row":{...}}` to add, and `PATCH .../rows/{row}` with `{"set":{...}}` to update or clear columns (`null`), and `DELETE .../rows/{row}` to remove a row. Schema pages use `next` as `after`; merge their columns until null. These routes bind to the calling applet principal; no instance id is needed and they cannot reach another applet. Pieces cards and flows use their existing `record`/`update` table actions. Table responses stay near 40 KB; follow `next` as `since` until null. Declared JSON columns include their descriptions in discovery. Portal-record applets must bind `ui.portal.records.table` and `.column` to a declared JSON column; the phone saves the result locally before queuing portal delivery.

The runtime derives `bridgit-applet-data/2` from these declarations for both old and new templates. Authors do not implement a separate discovery or export API. Installed-app listings return `data_url`; follow it to typed schemas, row counts, choice/status distributions, batch outcomes, `rows_url`, photo availability and authenticated photo links. The contract also exposes older/custom free-form records under `records`, with `{key,value,updated_at,chars}` and a `rows_url`; these pages use `next` as `after`. Each store advertises `cursor_parameter`. Every table row retains `id`, `at` and `by` alongside declared columns. Never rename ids merely to change labels; preserve rows and references during upgrades.

Agent review path: list installed applets, follow `data_url`, read table pages (`limit=200`, `next` passed as `since` until null), and download saved photos with the same Bearer header. `/data/export` returns JSON with all accessible `tables[].rows`; `?format=zip` includes `manifest.json` and original JPEGs. Exports are capped at 20 MB; larger datasets use pages and individual photo URLs. Inspect `complete`, `excluded_tables`, `media_complete`, and each photo's `available`. Reads are live, not an atomic snapshot. Missing media is reported, never recaptured. Whole photo reads are capped at 20 MB; larger originals support `offset`/`length` chunks of up to 8 MB (the response reports byte offset, total and next offset). Native applets without a package table store advertise `native_sources` for their existing status/history/frame APIs and `complete:false`; generic export is unavailable for those adapters. No model call, recognition rerun, template modification, reinstall, new owner approval or Android share sheet is needed to inspect data.

Template acceptance: install from the template; confirm `data_url` enumerates every durable table and typed column; write records through the normal flow; verify pagination returns every row exactly once while quiescent; check saved status matches the rows and batch outcome; export and resolve every photo ref. Check another paired control key can do the same, and applet execution principals cannot read another applet's private data.

Rules the phone enforces:

- **Blanks are whole values.** `{"$input": "camera"}` is replaced by the checked value of that blank. Nothing is spliced into text, so a value can't change a URL, a question or HTML.
- **Watch ids reach the card and the workflow.** `{"$watch": "main"}`, in `ui.card.sources`, a button, `ui.card.data` or `processing.workflow`, becomes the real `watch_id`. An HTML card's data goes into its `/*RECIPE*/…/*END RECIPE*/` block as JSON, with `<` escaped.
- **The workflow is the applet's flow.** A trigger (button, interval, charging, place, or `{"type":"watch","watch":{"$watch":"main"},"on":"match"}`) and up to 32 steps: `photo`, `ask_model` (Jev or Clef), `ask_owner` (waits for an answer), `wait`, `stop`, `notice`, `speak`, `ring`, `alert`, `event`, `record` (a table row). Later steps use earlier results (`{"$step":"look.answers.eating"}`), any step can have `only_if` and `on_error`, and every run is logged (`workflow.runs`). The owner's review shows the flow as one plain sentence. See [Flows](#flows) above.
- **Permissions are worked out from the parts.** The phone derives them from the watch data (camera → `camera`), rule and schedule calls, the card (`interactions`), and the workflow's scopes. If the file uses something it didn't declare, it is refused. The card's call sources and API buttons count too (a `GET /v1/weather` source adds `weather`). A card's calls run as the applet, so a call it didn't declare is refused.
- **Watches stay alive.** They get the longest lifetime the rules allow (24 hours, or 90 days with a tally) and are renewed while the applet is active. The card (7 days) is re-posted when it expires, unless the owner dismissed it.
- **Each part passes its own rules first.** Every part is checked by the same rules as the matching API call, before Approve is offered (`POST /v1/watches`, `POST /v1/interactions`, `POST /v1/schedule`, `workflow.validate`).
- **Paid calls have one cap per applet.** `"budget": {"day_usd": 0.5, "month_usd": 5}` (top level, 0.01-100 each) caps every paid cloud call the applet makes: watch Jev/Clef checks, `ask_model`, find, locate, appraise. Without it the phone uses $1 a day and $10 a month. This is separate from the phone's own monthly model budget (`model_usd_per_month` in `GET /v1/limits`, default $1.50, see decisions.md): every paid call must fit both, and the phone budget is checked first, so at the defaults it is the one an applet reaches first. Over the applet cap, paid calls fail with `budget_reached`; free on-phone checks go on. The owner sees the cap on the review and can change it in Installed applets.
- **Validate warns about known traps.** `POST /v1/applets/validate` returns `warnings` (code, where, says, fix) that never block an install: photo bytes sent from a card (a card's request is at most 16 KB), replies over a card's 64 KB, form submits and browser storage in a card, declared permissions nothing uses, a data_policy that says no remote models while the applet asks one, and paid calls without a `budget`.
- **Workflows need their Agent permissions feature on.** Workflow scopes are granted only for that workflow. Its feature (for example Local workflows) must be on in Agent permissions, or the review lists it as blocked.
- **Sources are limited.** The phone downloads only from https://bridgit.cc and Bridgit's template registry. An Import link may carry `sha256` of the file, and the phone refuses a file that doesn't match.
- **The Pet monitor is the built-in monitor.** Its registry template (`dog-monitor`, adapter `android.dog.v1`) installs the native monitor with the chosen camera.

## The applet's portal (its page on the device)

An applet's page (`ui.card`) is its portal: the one place the applet is used. **Open** in Installed applets shows it full screen, and a controlling agent with the Applet portals permission can show it too, read it and drive it without tapping (API revision 100). An applet whose web portal is its interface (`ui.portal.tables`, below) opens that web portal instead:

- `GET /v1/applets/portals` lists every applet with a portal. `POST /v1/applets/{id}/portal/open` brings it to the front.
- `GET /v1/applets/{id}/portal` returns `functions`, `state` (what the page published), `text` (its visible words) and `last_input` (the owner by touch, or an agent).
- `POST /v1/applets/{id}/portal/call {"function", "args"}` runs a function the page exposes and returns its answer. `POST …/portal/close` closes it.
- Events: `portal.opened`, `portal.functions`, `portal.state` (at most one a second) and `portal.closed` reach every agent that opened or called it, and the agent that installed it.

An HTML page offers functions with `Bridgit.portal`:

```js
Bridgit.portal.expose("add", {description: "Add to the count", params: {by: "integer"}});
Bridgit.portal.on("call", (name, args) => { if (name === "add") { count += args.by || 1; draw(); return {count}; } });
Bridgit.portal.setState({count});  // ≤ 16 KB; agents read it with GET …/portal
```

The page decides what each function does and what the screen shows. Limits: 32 functions, names `[a-z][a-z0-9_]{0,39}`, 16 KB for params, state, args and results. `Bridgit.portal.available` is false where the page isn't a portal, so one page works everywhere. A pieces page can be opened and read, but exposes no functions yet.

Cards (`POST /v1/interactions`) are something else: an agent's own screen for whoever is at the device (a kiosk, a question, a form). Applets don't need them.

## Web portal

An applet can have a private web portal at bridgit.cc/myapps, which the app also shows under **Applets › Portals** on phones and tablets, and which works in a browser on a computer. It needs something to show, declared under `ui.portal`:

- a watch with a `tally` (today's counts, each check's answer and the latest photo), or
- `records` (`{kind, title, table, column}`): results the card saves to the declared table’s described `json` column before sending with `POST /v1/applet/portal/record`, as words and numbers (for example each workout), or
- `tables` (1-3 of your `processing.tables` ids, API revision 99): the portal becomes the applet's interface. While it is on, the phone copies those tables' rows and photos to it and keeps them there until the portal or the applet is removed, and the card stays off the Cards inbox. `actions` lists the card's button ids the portal page may press on the phone: a camera button, a flow button (a batch shows its progress on the page) or a share step. Inside the app the page presses them at once; from a computer, an edit, a delete or a flow button waits for the phone's next check-in (about a minute), and camera and share buttons need the phone.

You choose how it is switched on with `ui.portal.include` (needs API revision 98):

- `"optional"` (the default): the review says the portal is off. The owner turns it on, and off, in Installed applets.
- `"always"`: the portal is part of the applet. The review says what it sends, it starts on Approve (or with the update that adds it), and it stops only when the applet is removed. A package with nothing to send is refused.

```json
"ui": {"portal": {"include": "always", "tables": ["photos", "items"], "actions": ["camera", "create", "export", "csv"]}, "card": {…}}
```

The Insurance inventory applet (`applets/insurance-inventory/applet.json`) is the worked example: its portal is its only screen.

## Applet pages (Spaces): one page for the web, the portal and Muse

One of an applet's standard options is a **page**: a gallery, a poll, a report or a walk-through that people see on the web and the owner sees in the Bridgit portal and in a Muse Space. You write it **once** in the `bridgit-page/1` format, and each host draws it its own way. Don't write host-specific versions: the format handles each host's chrome, data, actions and fallbacks.

- **Blocks**: the card pieces above, with the same fields (`header`, `status`, `text`, `note`, `metrics`, `gallery`, `video`, `table`, `timeline`, `people`, `devices`, `draft`, `buttons`), plus five page blocks:
  - `section` `{title, eyebrow?, collapsed?}`
  - `image` `{src, alt, caption?, frame: none|card|gilt, aspect?}`
  - `rich_text` `{html}`: sanitised. Allowed are `p h3 h4 ul ol li strong em a blockquote code pre br hr table…` and inline svg with static shapes; links must be `https:`.
  - `scenes` `{prompt?, items: [{label, says?, result?, image?}]}`
  - `vote` `{options, key, label, image?, into, per_viewer?, show_counts?, audience?, closes_at?}`

  Limits: at most 48 blocks, 8 sources and 64 KB per page.
- **Data**: the card `sources`, plus `{"snapshot": "<name>"}`. The portal reads them live. The web and Muse hosts read the snapshot the device publishes while the page is published. `reply` and `batch` sources work in the portal only.
- **Media** by reference only: `{"photo": "kept:…"}` or `{"$source": "…"}`, never bytes or URLs. Web and Muse pages get signed, expiring links.
- **Hosts**:
  - **Web**: the page on bridgit.cc. It ends with the **Get Bridgit footer by default**: the footer is the last thing on the page.
  - **Portal**: in the app, drawn natively, with no footer.
  - **Muse**: static HTML for a Space, with no footer. Scenes become a list, and a vote shows its counts and links to the web page.

From an agent key your phone minted (`https://bridgit-feedback.bridgit-app.workers.dev`, `Authorization: Bearer bgk_…`):

1. `PUT /v1/applets/installed/{applet}/pages/{page}` `{definition, expected_revision}`. The answer is **202 awaiting_owner**: the owner approves the page on the device. Waiting for approval is not success. Watch `GET …/events` for `page.approved` or `page.rejected`. `PATCH` `{patch, expected_revision}` changes fields (`null` clears one), and `DELETE` removes the page. An applet has at most 4 pages.
2. `POST …/publish` `{hosts: ["web","muse"], visibility: "link"|"signed_in"}`. The answer is **202 pending_owner**: publishing is sharing, so the owner approves it.
3. Once it is published, the web page is at `GET /v1/pages/{public_id}/html`. For a Muse Space, fetch `GET /v1/pages/{public_id}/export?host=muse` and place the HTML in the owner's Space. Fetch it again after each `page.approved`.
4. Votes from the web page reach the device as rows `{option, voter}` in the table the vote names (`into`). You see each vote as a `page.action` event, without the voter.
5. The footer is your decision: `PUT …/footer` `{get_bridgit: false, removed_reason: "…"}` removes it, which is audit-logged and needs no approval, and `DELETE …/footer` restores it. Leave it on unless there's a reason.

If the owner switched off your control of applets, changes answer `403 permission_off: controlling_applets`. Reads still work. Every write takes an `Idempotency-Key`. The worked example is the Karol Portrait Gallery: a `gallery` of portraits in gilt frames, a `vote` into a `votes` table, and a `table` with the tally.

```json
{"format": "bridgit-page/1", "title": "Karol Portrait Gallery", "theme": {"accent": "gilt"},
 "sources": {"portraits": {"table": "portraits", "limit": 24}, "votes": {"table": "votes", "limit": 500}},
 "blocks": [
  {"type": "header", "title": "Karol's Portrait Gallery", "text": "Vote for your favourite."},
  {"type": "gallery", "photos": {"$source": "portraits.items"}, "photo": "photo", "caption": "title"},
  {"type": "section", "title": "Vote for your favourite"},
  {"type": "vote", "options": {"$source": "portraits.items"}, "key": "id", "label": "title", "image": "photo", "into": "votes", "show_counts": true}
 ]}
```

## Runs on its own, or only when used

An applet with watches or a schedule runs on its own, and its budget's actions say how often. One with neither, whose flows only a card button (`called` or `button` trigger) starts, runs only when the owner uses it: it has no scheduled actions, and Installed applets shows **Open** for it (its card, or its portal when the portal is its interface). The Insurance inventory works this way.

## Not covered yet

- Custom logic beyond watches, rules, schedules and the workflow's step menu. There is no script step: packages are declarative, and `supports_dynamic_execution` stays false. A sandboxed script step is a possible later addition.
- Installing straight from an agent's own server URL. Send the file inline as `package` instead.

For registry creation, publishing, listing, forking and revision updates, see
[Manage a library applet](library-management.md). New portable packages use
`bridgit.package.v1`. A single button workflow can use `{"run_workflow":true}`;
to invoke a particular named called flow, use a card button action such as
`{"flow":{"$flow":"read"},"with":{...}}` with that flow's declared arguments.
A flow `photo` step uses scope `camera.snapshot`; a camera watch requests
`camera`. Declare the permissions required by the parts actually used.

When `ui.card.data` is present on an HTML card, include both literal markers
in executable JavaScript, for example:

```html
<p id="watch"></p>
<script>
  const config = /*RECIPE*/{}/*END RECIPE*/;
  document.querySelector("#watch").textContent = config.watch_id || "";
</script>
```

For `"data":{"watch_id":{"$watch":"main"}}`, the installed applet fills this
object with the new watch id. Use DOM text properties for displayed values.
Hash the final UTF-8 asset bytes, including the trailing newline if present.

For a tally watch, choose `gap_s` at least as large as the sampling interval
and no greater than 21,600 seconds. If the owner can change the interval, choose
bounds that still satisfy the rule at both ends of the allowed range.
The Android watch host also accepts `label_gap_s` to set an episode gap for a
specific tracked label. For example, `"gap_s":60,"label_gap_s":{"resting":120}`
allows a longer break between resting sightings while coverage still uses 60 seconds.
Each override takes a whole number from 1 to 21,600 seconds.

## Required interaction standard

Follow [the applet interaction standard](applet-interaction-standard.md). Person-started photo/video actions use a native viewfinder, camera flip, recording timer and review with Use/Delete and optional video playback. Card/portal requests cannot opt out; automatic monitoring remains background. Every long action needs visible progress and immediate button feedback.

## Local images and package icons

To give an applet a PNG icon, set `ui.icon` to the asset name, for example
`"blue.png"`. In your authoring file write
`"assets":{"blue.png":{"media_type":"image/png","path":"images/blue.png"}}`.
Place the image under the authoring file's directory. Use a PNG up to 48 KiB
and 1,024 pixels per side. Text assets can use the same local-file syntax.
Download and unzip the [offline authoring kit](https://bridgit.cc/applets/authoring/bridgit-applet-authoring-v1.zip).
From the kit directory, use Python 3.9 or later for packing and Java 17 or later
for validation. Keep source and output filenames distinct.

```sh
python3 pack-applet.py source.json > applet.json
java -jar validate-applet.jar applet.json
```

The validator prints JSON on stdout. Read `valid` and `error` on a rejected
package. On success, compare `required_scopes` with your intended permissions.
The `not_checked` list identifies checks that still require a host or an account.
The archive includes the step inventory, service catalog and working examples.
Developers in an Android checkout can also run `tools/validate-applet.sh`.

The packer reads the files locally. In the output a PNG has `media_type`,
canonical padded `base64`, decoded byte count `size`, and lowercase `sha256`
of its decoded bytes. Text has `text` and `sha256` of its exact UTF-8 bytes.
You can author that JSON directly. The whole file must fit in 128 KiB.
Send the packed definition when creating a revision. An authorized exact
revision read returns the self-contained definition, including its assets,
so you can export it for offline use.

Set `start_paused: true` in a watch request to wait for an explicit resume before taking the first reading or firing rules. This applies at creation. Subsequent launches restore the saved pause state. A paired Android host honors this field for camera and sound watches.

Use `tally.typical_gap_basis: "continuous_seen"` when an interval between two episodes is meaningful only if the subject stayed in view. The median uses consecutive episode starts within a single observed span. A failed reading, a failed visibility test, or silence longer than `gap_s` ends the span. The result is omitted until there is one covered pair. The default `"elapsed"` uses wall-clock gaps once three episodes have occurred.

## Required practice contract

Before creating or changing an applet, read [the practice contract](https://bridgit.cc/learn/builder/applet-practices.md) and [catalog](https://bridgit.cc/learn/builder/practices.json). Record the catalog review in `ui.practices`. The validator reports applicable practices, defaults and checks. Run the named behavioral checks; unverified is not passed. Use a justified exception only for its exact target. Reassess exceptions when the target changes.
