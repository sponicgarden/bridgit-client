What runs where

  • Explicit refresh → phone returns enrolled device inventory without a probe → dashboard.
  • The phone must be on the supported direct LAN for an authorized status action; the controller may connect remotely through direct or relay transport.

Controller integration

  • Controller or owner performs credentialed verification/enrollment using supported adapters; not part of this learning example.
  • Retain checked_at per successful status response. Stop polling on pause/stop and cancel the card.

Only explicit decision-model/weather requests leave the phone; direct or relay transport still requires a running reachable phone.

Boundaries

  • Listing does not test devices: availability=not_checked is not online. Discovery is partial and unverified; enrollment is separate.
  • No enrollment credentials are embedded. No relay switch, motor, light or other physical action is run by the template.

Lifecycle

start

Configure card data, POST the generated HTML interaction; this does not automatically capture or poll.

update

Owner explicitly refreshes; controller stores approved data and posts a replacement card as needed, cancelling old pending cards.

pause

The Pause button suspends this card’s controls and suppresses results from a pending refresh. There is no background job in this starter; an in-flight capture may finish. Controller integrations must separately pause their jobs.

stop

The Stop button stops this card, suppresses late results, and requests controller shutdown through one response. Confirm/close the controller job and DELETE the interaction separately. Local stop is not proof that an external process stopped.

Failures and costs

  • No enrolled devices: show empty. A failed status call does not prove a device is offline.
  • Unsupported adapter: display its actual advertised actions, do not substitute arbitrary URLs or claim universal smart-home support.
  • No remote inference. LAN availability depends on phone/network and owner-approved enrollment.
